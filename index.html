DAY 00

底层概念：模型到底在做什么

先建立一张因果图：文本被切成 token → token 进入有限上下文 → 模型计算下一个 token 的概率 → 采样得到输出 → 客户端接收流并决定是否执行工具。

1. Token 与分词

前端类比：字符编码 + 编译器词法分析

模型不直接读取“字”或“单词”，而是把文本映射成词表里的整数 ID。一个 token 可能是一个汉字、词片段、标点或空格；同一句话在不同 tokenizer 下数量可能不同。模型真正处理的是 ID 序列，因此费用、延迟和上下文占用通常按 token 计算，而不是按字符数计算。

因果链：更长输入 → 更多 token → 更多注意力计算与上下文占用 → 成本和延迟上升。字符数只能粗估，生产中应读取 API 返回的 usage。

2. 上下文窗口

前端类比：内存预算，不是硬盘

上下文窗口是一次推理中可见的 token 总预算，通常同时包含 system、历史消息、工具定义、检索内容和待生成输出。模型没有自动读取你上一次请求的“长期记忆”；你不重发，它就看不见。

  • 历史越长，留给本次输出的空间越少。
  • 超过限制时，请求会失败或内容被截断；不能只靠“无限追加 messages”。
  • 工程做法是预算、裁剪、摘要或检索，而不是把所有内容都塞进去。

3. Temperature / top_p

前端类比：对候选列表先改权重，再过滤

模型先为“下一个 token”产生一组分数（logits），经 softmax 变成概率。temperature 缩放分数：接近 0 时分布更尖、更偏向最高概率；升高后分布更平，低概率候选更有机会。top_p 则从高到低保留累计概率达到阈值的最小候选集合，再在其中采样。

不要误解：temperature 不是“创造力按钮”，top_p 也不提高事实准确率。它们只改变抽样分布；同样输入仍可能因采样或服务端实现而变化。调试时通常固定一个、只改另一个。

4. 系统提示词

前端类比：高优先级配置 + 接口契约

聊天模型在训练阶段学会区分 system、user、assistant 等角色，因此 system 内容会作为高优先级条件影响后续 token 的概率分布。它有效，是因为模型被训练去遵循这种消息结构，不是因为存在一个绝对安全的“系统权限”。

  • 它适合声明角色、边界、输出结构与决策规则。
  • 它不能替代参数校验、鉴权或敏感操作确认。
  • 清晰的约束能提高命中率，但提示注入仍需程序侧防守。

5. SSE 的本质

前端类比：单向事件流，对照 WebSocket 双向连接

SSE 是一个保持打开的 HTTP 响应，服务端按 data: 事件持续写入文本，客户端边读边渲染。聊天生成主要是服务端向客户端单向推送，因此无需为双向实时通信引入 WebSocket 的协议和连接管理成本。

关键边界：网络 chunk 不等于 SSE 事件，更不等于 token。UTF-8 字节、事件行和 JSON 都可能被拆开，所以客户端需要 TextDecoder 与 buffer。

6. Function Calling

前端类比：事件回调 + dispatcher

模型不会进入你的运行时调用函数。它只是根据工具 schema 生成结构化文本：工具名和参数。客户端像事件分发器一样校验意图、调用白名单函数、把结果作为 tool 消息回传，再让模型生成最终回答。

闭环：模型提议 → 程序校验 → 人类按需确认 → 程序执行 → 结果回传 → 模型组织答案。权限永远在程序和人手里。

准备环境

我们采用 React + Vite 做界面，Node.js 做轻量代理。浏览器永远不直接持有 API Key。

开始前确认

  • Node.js 20 或更高版本
  • 一个可用的 DeepSeek API Key
  • VS Code 与终端
  • 会使用基本的 Git 命令

项目结构

src/ 放 React 界面，server/ 放代理接口，.env.local 只存本机密钥。前后端分开，是为了避免把密钥打进浏览器代码。

1. 创建项目

TERMINAL
npm create vite@latest llm-chat -- --template react-ts
cd llm-chat
npm install
npm install express cors dotenv
npm install -D tsx @types/express @types/cors
mkdir server
为什么这样做

Vite 提供最小 React + TypeScript 客户端；Express 只承担密钥隔离和流转发。先把浏览器职责与可信服务端边界分开，后面替换模型供应商时无需改界面。

2. 保存密钥

.env.local
DEEPSEEK_API_KEY=替换成你的密钥
为什么这样做

.env.local 是运行时配置，不是前端源码。它让服务端读取密钥，而不会被 Vite 打包进可下载的 JavaScript；这和前端不能保存数据库密码是同一条信任边界。

密钥红线

不要写进 src/，不要使用 VITE_ 前缀，也不要提交到 Git。确认 .gitignore 包含 .env*。

动手任务 1

证明密钥没有进入前端包

  1. 运行 npm run build。
  2. 在 dist/ 内搜索密钥前 6 位和 DEEPSEEK_API_KEY。
  3. 两者都应搜不到；若搜到，删除前端引用并重新构建。

完成证据：保留终端“0 个匹配”的截图，写进 README 的安全说明。

出错先看这里

import dotenv from "dotenv";

dotenv.config({ path: ".env.local" });
const app = express();
app.use(cors());
app.use(express.json());

app.post("/api/chat", async (req, res) => {
  try {
    const upstream = await fetch(
      "https://api.deepseek.com/chat/completions",
      {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          Authorization: `Bearer ${process.env.DEEPSEEK_API_KEY}`,
        },
        body: JSON.stringify({
          model: "deepseek-chat",
          messages: req.body.messages,
          stream: true,
        }),
      }
    );

    if (!upstream.ok || !upstream.body) {
      return res.status(upstream.status).send(await upstream.text());
    }

    res.setHeader("Content-Type", "text/event-stream");
    const reader = upstream.body.getReader();
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      res.write(Buffer.from(value));
    }
    res.end();
  } catch (error) {
    res.status(500).json({ error: "代理请求失败" });
  }
});

app.listen(3001, () => console.log("API: http://localhost:3001"));
为什么这样做

代理不解析模型内容，只保管密钥、检查上游状态并把字节流向下游转发。res.write 保持响应开放，避免等待完整回答；upstream.ok 则阻止把错误页伪装成正常 SSE。

2. 客户端读取 SSE

核心读取函数 · src/App.tsx
async function streamReply(messages: Message[], onToken: (t: string) => void) {
  const response = await fetch("http://localhost:3001/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ messages }),
  });
  if (!response.ok || !response.body) throw new Error("请求失败");

  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split("\n");
    buffer = lines.pop() ?? "";

    for (const line of lines) {
      if (!line.startsWith("data: ")) continue;
      const data = line.slice(6);
      if (data === "[DONE]") return;
      const token = JSON.parse(data).choices[0]?.delta?.content;
      if (token) onToken(token);
    }
  }
}
为什么这样做

getReader() 读取的是字节块，TextDecoder 负责保持跨 chunk 的 UTF-8 解码状态，buffer 负责保持跨 chunk 的事件状态。两层状态都保留，中文字符或 JSON 被截断时才不会随机报错。

为什么要保留 buffer？

网络分块不保证刚好按一行切开。一个 JSON 片段可能跨两个 chunk；先累积，再按换行取完整事件，才能避免随机解析失败。

src/App.tsx · 完整可运行组件
import { useState, type FormEvent } from "react";

type Message = {
  role: "system" | "user" | "assistant";
  content: string;
};

async function streamReply(messages: Message[], onToken: (token: string) => void) {
  const response = await fetch("http://localhost:3001/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ messages }),
  });
  if (!response.ok || !response.body) throw new Error("请求失败");

  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split("\n");
    buffer = lines.pop() ?? "";
    for (const line of lines) {
      if (!line.startsWith("data: ")) continue;
      const data = line.slice(6);
      if (data === "[DONE]") return;
      const token = JSON.parse(data).choices[0]?.delta?.content;
      if (token) onToken(token);
    }
  }
}

export default function App() {
  const [messages, setMessages] = useState<Message[]>([
    { role: "system", content: "你是简洁、准确的编程助教。" },
  ]);
  const [input, setInput] = useState("");
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  async function send(event: FormEvent) {
    event.preventDefault();
    const text = input.trim();
    if (!text || loading) return;

    const userMessage: Message = { role: "user", content: text };
    const next: Message[] = [...messages, userMessage];
    setInput("");
    setError("");
    setLoading(true);
    setMessages([...next, { role: "assistant", content: "" }]);

    try {
      await streamReply(next, (token) => {
        setMessages((current) => current.map((message, index) =>
          index === current.length - 1
            ? { ...message, content: message.content + token }
            : message
        ));
      });
    } catch (cause) {
      setError(cause instanceof Error ? cause.message : "未知错误");
    } finally {
      setLoading(false);
    }
  }

  return (
    <main>
      {messages.filter((message) => message.role !== "system").map((message, index) => (
        <p key={index}><b>{message.role}:</b> {message.content}</p>
      ))}
      {error && <p role="alert">{error}</p>}
      <form onSubmit={send}>
        <input value={input} onChange={(event) => setInput(event.target.value)} disabled={loading} />
        <button disabled={loading || !input.trim()}>{loading ? "生成中…" : "发送"}</button>
      </form>
    </main>
  );
}
为什么这样做

messages 是发给模型的临时工作内存，类似 Redux 中的显式状态：每次请求都提交一个确定快照。先插入空 assistant 项，再逐 token 更新最后一项，可让 UI 只维护一条正在增长的消息。

Prompt 不是“咒语”，而是接口契约

先写清角色、任务、约束与输出格式，再用输入样例测试。提示词和代码一样要能版本化、能回归验证。

system-prompt.ts

Function Calling：让模型学会“请求工具”

模型不会直接执行函数。它只输出一个结构化的调用意图，你的代码验证参数、执行函数，再把结果交回模型。

用户提问
→
模型返回 tool_call
→
代码执行并回传结果

声明一个安全、可验证的工具

tools.ts
const tools = [{
  type: "function",
  function: {
    name: "calculate",
    description: "计算两个数字的加减乘除",
    parameters: {
      type: "object",
      properties: {
        a: { type: "number" },
        b: { type: "number" },
        operation: {
          type: "string",
          enum: ["add", "subtract", "multiply", "divide"]
        }
      },
      required: ["a", "b", "operation"]
    }
  }
}];
为什么这样做

schema 是模型与执行器共享的调用协议，类似前端事件的 payload 类型。枚举收窄候选动作，required 保证必要字段存在；真正运行前仍要在服务端做运行时校验，因为模型生成的 JSON 不受 TypeScript 类型系统保护。

不要把模型输出当成可信输入

执行前必须校验工具名、参数类型与范围。涉及写文件、发消息、付款等操作时，还需要明确的人类确认；不要让模型自由拼接并执行 shell 命令。

你要理解的闭环

  1. 第一次请求携带 tools。
  2. 若响应包含 tool_calls，由你的代码解析参数并执行对应函数。
  3. 把 assistant 的调用消息和 role 为 tool 的结果都追加进 messages。
  4. 第二次请求让模型根据工具结果组织自然语言答案。
动手任务 5

让工具失败一次，再完成闭环

  1. 让用户输入“10 除以 0”，在执行器中拒绝非法参数。
  2. 把结构化错误作为 tool 消息回传，要求模型解释失败原因，而不是伪造结果。
  3. 再用正常参数运行一次，并在日志中打印 tool_call、校验结果和最终回答。

完成证据：保留成功与失败两条 trace；你要能指出模型负责决策、程序负责执行的边界。

  9. 你用的向量库数据量和性能怎样？用真实规模、索引参数、P95 延迟与瓶颈定位数据回答。
  10. 一次 RAG 输入在系统内怎样流动？从 query 处理到证据拼装与答案引用，画出端到端链路。
  11. 向量检索和关键词检索有何区别？语义相似适合改写表达，关键词适合实体精确命中，生产常做混合。
  12. Query Rewrite 为什么做，怎么做？把口语、歧义和上下文依赖改成可检索查询，并防止语义漂移。
  13. 什么是多路召回？并行使用稠密、稀疏、规则等通道，再融合去重与重排。
  14. RAG 检索优化有哪些策略？从 query、索引、召回、rerank、上下文拼装和反馈逐层优化。
  15. 了解哪些复杂 RAG 范式？说明 Self-RAG、Corrective RAG 等在哪个环节增加判断与纠错。
  16. 什么场景用图数据库增强检索？当关系路径、实体约束和多跳推理比纯语义相似更关键时采用。
  17. 如何规避 RAG 幻觉？从提高证据质量、强制引用、拒答策略和事实核验共同治理。
  18. 怎样量化 RAG 效果？拆成检索召回、重排、答案忠实度、相关性与端到端任务成功率。
  19. 知识库如何动态持续更新？用增量解析、版本化索引、删除同步和回滚保证新旧一致。
  20. RAG 落地最难的地方是什么？用自己的失败案例说明数据质量、评测闭环和业务边界最难。

LLM 工具调用面试题 16 题 · 阶段一重点
  1. 什么是 Function Calling？原理是什么？模型生成结构化调用意图，客户端校验执行并回传结果，不是模型直接运行函数。
  2. LLM 如何学会调用外部工具？从带工具描述与调用样本的训练数据解释“选择工具并生成参数”。
  3. Function Call 能力怎样训练出来？概括监督微调、偏好优化与执行反馈，不把 schema 误当运行能力。
  4. 什么是 MCP？核心内容是什么？把它说明为连接模型应用与外部能力的标准上下文协议。
  5. MCP 由哪些部分组成？围绕 host、client、server 与资源/工具/提示的交互边界回答。
  6. MCP 和 Function Calling 有什么区别？FC 是模型输出调用的机制，MCP 是能力发现与连接协议，可组合使用。
  7. 何时用 Function Calling，何时用 MCP？少量内置工具直接 FC；跨应用复用、标准接入与动态发现考虑 MCP。
  8. 为什么有些推理模型不支持 MCP？先澄清 MCP 在应用层，再分析模型结构化输出与工具训练能力是否匹配。
  9. Skill 是什么？把完成一类任务的知识、流程和资源封装成可复用操作手册。
  10. MCP 和 Agent Skill 有何区别？MCP 提供可连接能力，Skill 描述如何组合能力完成任务。
  11. Function Calling、Skill、MCP 三者是什么关系？用“调用语言、操作手册、工具箱协议”建立分层关系。
  12. A2A 与 MCP 有何区别？A2A 处理 Agent 间协作，MCP 处理应用与工具/资源连接。
  13. MCP 通常采用什么通信方式？从本地 stdio 与远程流式 HTTP 说明传输只承载协议消息。
  14. WebSocket 和 SSE 有何区别与局限？比较双向/单向、协议复杂度、断线恢复、代理兼容与聊天场景需求。
  15. WebRTC 与 WebSocket 在 AI 对话流中有何差异？实时音视频优先 WebRTC，通用双向应用消息更适合 WebSocket。
  16. LLM 网关解决什么问题？统一鉴权、路由、限流、重试、观测、成本和多模型切换。

大模型工程面试题 22 题 · 应用必修 + 算法岗选看
  1. 什么是大语言模型？与传统 NLP 模型有何区别？从规模化预训练、通用生成能力与任务适配方式对比。
  2. Transformer、Encoder、Decoder 的基本原理是什么？围绕注意力、前馈网络、残差与自回归目标说明信息流。
  3. MHA 有何局限？MQA、GQA、Flash Attention 怎么解决？从显存带宽、KV 头共享和 IO 优化解释各自代价。
  4. 位置编码有什么用？sin/cos、RoPE、ALiBi 有何区别？先说明注意力缺乏顺序，再比较绝对、旋转与偏置式位置表达。
  5. 分词器是什么？原理是什么？文本映射为词表 ID，词表与算法决定 token 数、成本和多语言表现。
  6. 大模型是怎样训练出来的？按预训练、指令微调、偏好对齐与评测部署讲全景。
  7. Scaling Law 与涌现能力是什么？说明数据、参数、算力的经验规律，并谨慎区分连续提升与阈值现象。
  8. 大模型微调有哪些方案？比较全量、PEFT、提示微调等在数据、显存和能力改变上的取舍。
  9. LoRA 除了减少参数还有哪些优点？讲低秩增量、可插拔权重、较低存储与多任务切换。
  10. RLHF、DPO、GRPO、拒绝采样是什么关系？从反馈来源、优化目标、是否显式奖励模型与在线采样区分。
  11. DPO 与 PPO 有何区别？比较直接偏好优化和强化学习策略优化的训练链路与稳定性。
  12. 贪心、Beam Search、采样何时使用？用确定性、搜索宽度、多样性与任务目标解释选型。
  13. temperature、Top-P、Top-K 控制什么？先讲 logits 到概率，再讲温度缩放与候选集合截断。
  14. KV Cache 与 Prompt Caching 原理是什么？一个复用自回归注意力中间状态，一个复用相同前缀计算或计费结果。
  15. 量化是什么？INT8、INT4、AWQ、GPTQ 怎么选？以精度、显存、吞吐、硬件支持和校准成本权衡。
  16. 如何写好 Prompt？明确角色、任务、上下文、约束、输出格式，并用评测集迭代。
  17. 什么是 CoT？为何有效，有何局限？把复杂问题拆成中间步骤，但要说明成本、错误累积与不可验证性。
  18. 幻觉为什么出现，如何缓解？从概率生成、训练知识与上下文不足解释，再用检索、工具、约束和核验治理。
  19. MoE 是什么？为什么 DeepSeek、Qwen 使用它？每个 token 只激活部分专家，用路由换取更大容量与较低计算。
  20. vLLM、TGI、llama.cpp、SGLang 怎么选？按云端吞吐、本地轻量、硬件、并发、生态与运维要求选型。
  21. 大模型能力评测指标有哪些？区分通用 benchmark 与业务任务集，补充正确性、延迟、成本和安全。
  22. 项目为什么选这个模型？用真实业务测试集比较质量、延迟、价格、上下文、工具能力和稳定性。

FDE 专题

一句话定位：以客户业务结果为目标、仍然直接写生产代码的工程岗位；核心是从模糊问题出发完成需求发现、方案设计、编码集成、生产上线、采用推广和反馈闭环。

能力维度面试官想确认什么
问题发现与拆解能否把“我们想用 AI”转成明确用户、现有流程、约束条件和可验证目标。
工程与 AI 系统设计能否设计可接入现有系统、可评测、可观测且可回滚的生产方案。
编码与调试能否在陌生代码、脏数据和变化需求下快速定位问题并可靠实现。
客户与项目推进能否管理承诺、冲突、范围、采用过程和高压事故，而不丢失业务目标。
产品化反馈能否区分一次性定制与可复用能力，并把现场反馈沉淀进产品。

高频题方向

  • FDE 与后端工程师、架构师、顾问有什么区别？答题思路：用结果责任、是否直接写生产代码、工作地点/协作边界、需求确定性四个维度对比；不要只讲岗位名称。
  • 客户只说“我们想用 AI”，你怎么拆解？答题思路：先找用户与高频流程，再建立基线、风险和约束，最后把目标改写成可测的任务成功率、时延、成本或采用率。
  • 如何设计可接入现有系统、又可回滚的生产方案？答题思路：画出现有接口与数据边界，采用小流量试点、版本化配置、降级路径、审计日志和回滚触发条件。
  • 进入陌生代码库后怎样调试线上问题？答题思路：先复现与收集 trace，缩小到输入、依赖、状态或基础设施，再做最小修复、回归测试和知识沉淀。
  • 客户现场发生范围冲突或高压事故，怎么处理？答题思路：先统一事实和影响，明确决策人、止损动作与时间盒；把范围、承诺和未决风险书面化，再持续同步。
  • 怎样区分一次性定制与可复用产品能力？答题思路：看需求是否跨客户重复、能否抽象稳定接口、维护成本与战略价值；对通用部分产品化，对例外保留配置或插件边界。
